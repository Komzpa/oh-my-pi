Requirement audits use the exact assigned IDs, one row per requirement; NEVER append letter suffixes or invent split IDs.
Receipt columns follow the canonical header supplied in QA AUDIT INPUT, located by name rather than position; literal pipes inside cells MUST be escaped as \|. Rows for unrelated parent IDs are ignored before field validation. Additional requirement IDs are recorded only when linked to the same assigned TODO row; missing or duplicate assigned IDs, mixed parent/sub-row IDs, differing clause artifacts, malformed assigned verdicts, wrong rows, changed source snapshots, and stale artifact identities remain rejected. Authenticated suffix sub-rows fold into their exact assigned parent with all clause evidence: fail beats unverifiable beats pass; every clause MUST name the same artifact. Raw words are OPTIONAL context, not identity; the authenticated assignment binds canonical owner words. A newly accepted receipt for the current artifact supersedes the prior verdict for that row, including fail → pass; an older artifact cannot overwrite a newer verdict.

Classify requirement candidates with op="classify": id is the Rn, classification is linked (needs rows with exact todo row contents), not-a-requirement (needs reason), or merged (needs mergeInto with another Rn). Example: op="classify", id="R1", classification="linked", rows=["<exact todo row>"].
Already-classified requirements remain immutable without a later owner scope change. To apply that change, cite its exact newer Rn with `supersededBy="R14"` and a nonblank reason in `classify`; the ledger records old/new classification and rows without rewriting source or history. Example: `op="classify", id="R5", classification="not-a-requirement", supersededBy="R14", reason="R14 cancels the fold rows"`. NEVER invent an owner statement or reuse an earlier superseding statement to reverse the owner's latest scope.
