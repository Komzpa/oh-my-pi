# Reemxy extensions

## Git commit identity

Every commit consumer (`git-pr-owner`, `coder`, and `workhorse`) checks effective author and committer identities and their config provenance before a new commit, uses configured real identity without invented agent identity overrides, and reads back both identities after committing. Local identity takes precedence over global identity; missing or invalid identity fails without creating a commit; amend, cherry-pick, and rebase retain the existing genuine contributor author.

## Presence settings

`goal_deadlines` derives the user’s timezone from persisted goal state (`state.timezone`), then falls back to the process `Intl` timezone.

Optional `reemxyPresence` is the package’s single settings key. Put it in OMP user or project settings; project fields override user fields:

```yaml
reemxyPresence:
   activeMinutes: 15
   awayMinutes: 30
   quietStartHour: 23
   quietEndHour: 9
   atRiskMinutes: 60
```

Hours are normalized to `0..23`; absent or invalid fields retain defaults.

## Durable user deadlines

`goal_deadline(action=set)` persists in the existing `reemxy-goal-deadlines` session entry even without a focused goal; no goal is invented. Its user authority and original final time live outside the experimental notes. Presence and deadline context retain the constraint after compaction, focus changes, and stage delivery. At the exact due time, context switches to **WRAP-UP MODE**: ship the best verified state, list unfinished work, and send one honest status message. A durable final-message receipt prevents repeated status demands. The tool resolves the epoch itself from `stages[].local_time` (`19:00` = next such moment, or `2026-10-21 19:00`) plus the timezone; `deadline_at` is only a cross-check (mismatch over a minute is rejected with the resolved value). A new user deadline more than 5 minutes past or more than 7 days ahead is rejected as an arithmetic error, and a wrong value set from the same user message may be corrected within 30 minutes (a self-extension still needs a newer user message).

The existing `tool_call` gate refuses new `todo init`/`todo append` rows and `task` spawns after a missed deadline. Its refusal asks the agent to get a new deadline time or a decision to drop the deadline from the user; nothing else (corrections, synthetic messages, assistant promises) reopens new work. Existing-row edits and wrap-up operations remain allowed; staffing demands, escalation, and idle staffing wakes stand down. The no-deadline path is unchanged.

A newer real user message explicitly giving a local `HH:MM` time can replace the deadline with `action=set` and `user_message` quoting that message. Assistant ETA/status promises cannot replace it. The user drops a live constraint in their own words (or `/deadline close`); `action=clear` quotes that newer real user message in `user_message`. The consumer replay fixture projects the original session's deadline input, no-focus save, exact due boundary, and notes rewrite; oracle: `user-deadline-replay.test.ts`.

Scope freezing on a **wrap-up request before the deadline**, and semantic recognition of arbitrary natural-language approvals, are not implemented here. Their owner is `todo_dispatch.ts`'s `input`/`isCorrectionInput` scope interpretation plus `goal_deadlines.ts`'s new-work `tool_call` gate; corrections must remain edits to existing rows rather than implicitly approve new rows.


## Subagent model selection

The extension no longer picks models. Each agent profile names role groups (`@free`, `@fast`, `@code`, `@vision-code`, `@judgment`, `@strong`) in its `model:` frontmatter; the owner defines the groups as `modelRoles` in `config.yml`, and core resolves the chain, picks the first credentialed entry and falls back through the rest. A role missing from config falls back to `default` in core. Effort is not set in profiles: `defaultThinkingLevel: auto` decides.

A re-dispatch of a Todo row after a rejected completion or a model-attributable failure takes the next entry of the agent's own chain whose vendor (model maker) the row has not tried yet (core, `task/redispatch-vendor.ts`).

`/brrrr` applies the config preset `brrrr` to the current session through core session presets (children inherit it); `/brrrr off` clears it. Without core session-preset support the command says so and does nothing.

What stays here: the write-scope gate (one non-isolated writer per checkout), the empty/shrinking-write refusal, and spawn/outcome records in `~/.local/state/omp-agent-router/spawns.jsonl` (`chosen` is the first candidate of the chain; the outcome's `resolvedModel` is what core ran). Oracles: `agent_router.test.ts`.

## Bounded worker supervision

Every row-executing profile must target about 15 minutes of work. If an assignment clearly will not fit or context approaches compaction, the worker stops at the next checkable result, reports completed work with a receipt, and proposes a split of what remains.

`todo_dispatch` must issue a non-blocking PLAN CHECK once per active worker when its child session compacts or its run exceeds 15 minutes. The notice identifies the worker and condition, asks the lead to request done/left through `write agent://<id>`, then split the remainder. A ten-minute worker without compaction must not be named; the silent-15-minute notice remains independent. The oracles are `agent_router.test.ts` and `todo_dispatch.gates.test.ts`.

## Retrospective gate reset

The "retrospective due" line reads `retrospective due (<reason>): read the Retro block in the final answer of the N workers who finished since <time> from agent://<id> (do not write to them; a missing block is recorded as missing), then retro-facilitator (skill://chief-of-staff Retrospective): <ids>`. A retro-facilitator `task` result clears the due flag and the notified-trigger key together: `retroDueReason`, `goalWorkStartedAt`, `reopenedRows`, and `retroDueNotifiedKey` all reset, so a later trigger with the same reason and deadline/delivery key notifies again. Cancelled/aborted worker jobs are never added to `workerFinishes` and so never appear as retro participants, though they still count as seen so they are not reprocessed. While a trigger's reason, deadline/delivery key, and finished-worker roster stay unchanged, the "retrospective due" line is emitted once and omitted from every subsequent PLAN CHECK; a new worker finishing under the same trigger changes the roster and reopens the notice. The oracle is `todo_dispatch.retro.test.ts`.

## Waiting on ready work

The wait gate normally lets the chief wait when open work depends on real outputs or user approval. Critical chains with free capacity receive the one-time split check below.

1. **Waiting on running work or on the user is allowed.** After any critical-chain split demand is answered, or outside that case, `wait` passes (no block, no capacity notice) while at least one task worker runs when every open row without a running worker either depends on a row owned by a running worker, or is `blocked` awaiting user approval of a proposal the chief has recorded. Example: 3 running workers, row A depends on a running worker's row, row B awaits user approval of a recorded proposal: the wait is allowed. Rows in these two states are never counted as parked, idle or unused capacity in any notice. Oracle: `todo_dispatch.wait.test.ts`.
2. **Shown capacity is capacity that can start.** Every worker-capacity number the package shows (wait refusal, chief refusal, MANDATORY REPLAN, PLAN CHECK, `Task cap=`) equals the number of workers that can start now: the Task cap bounded by the machine and the count of unique provider/model routes that pass the live, authenticated, non-depleted check used by `agentHasLiveModel` in `agent_router.ts`. A fixed or configured cap is never shown as free slots that no provider can fill; with no startable route the shown capacity is 0. Oracles: `agent_router.test.ts`, `todo_dispatch.test.ts`, `todo_dispatch.wait.test.ts`.
3. **Ordinary staffing refusals are noticed once.** Refusal notices are deduplicated by their content, not by an internal key: a refusal whose rendered content is identical to the previous refusal notice is not delivered again, whether or not the plan revision or any other internal key changed. Repeating the same `wait` returns no block and no new notice until the refusal content differs. Oracle: `todo_dispatch.wait.test.ts`.
4. **Clock times use the user's timezone.** Every clock time in a notice (`due HH:MM`, `P95 HH:MM`, `compacted at HH:MM`, past-P95 check-ins) is rendered in the timezone `goal_deadlines` derives (persisted `state.timezone`, else the process `Intl` timezone), never raw UTC. With `TZ=Asia/Tbilisi`, a P95 of 19:16Z renders as `due 23:16`. Oracles: `goal_deadlines.test.ts`, `todo_dispatch.gates.test.ts`.
5. **Work with no commit is surfaced, never aborted.** A running worker, an `in_progress` row, or a wait that has run for more than 15 minutes since the worker's spawn or resume with no new commit in that worker's worktree is marked `⚠ <N>m no commit` (for example `⚠ 17m no commit`) on its TODO row and HUD line, and is listed first in PLAN CHECK as `suspect: <row> · <worker> · <minutes> · <last line>`. The chief answers each suspect with an action or a one-line explanation. The harness never aborts, cancels or re-dispatches the worker for this. A worker whose worktree gained a commit within the last 15 minutes, or that has run 15 minutes or less, is not marked. Oracles: `todo_dispatch.gates.test.ts`, `interactive-mode-todo-clear.test.ts` (coding-agent).
6. **A worker is shown once.** A running worker appears exactly once across the TODO section and the Subagents list: on the TODO row it owns when it owns an open row, otherwise in Subagents; never on both surfaces. Oracles: `subagent-hud-render.test.ts`, `interactive-mode-todo-clear.test.ts` (coding-agent).
7. **Owned work survives collapse.** An `in_progress` row owned by a running worker stays visible when the TODO section or its stage is collapsed. Oracle: `interactive-mode-todo-clear.test.ts` (coding-agent).
8. **`OMP_LANE_UNIT` is a single-writer lane.** When the variable is set, including to an empty value, the extension does not register staffing requirements, refuse tools to compel worker staffing, inject chief-of-staff role/advice/PLAN CHECK or retrospective notices, or enqueue automatic continuation wakes. This mode overrides the chief-gate, retrospective and wake outputs above; non-staffing safety controls remain active. Oracle: `todo_dispatch.wait.test.ts`.

Negative controls, unchanged outside `OMP_LANE_UNIT` mode: a truly idle row (dependency-ready, not awaiting approval, no exact running owner) with free startable capacity still refuses the wait, and so does waiting with nothing running. That refusal identifies the row and its recorded owner, states that the owner is not running, and gives one conditional repair: set `schedule.owner` with `todo schedule` if a running worker already does that row; otherwise start a worker for it. A single ready row is never framed as unused machine capacity. A failing service or failed task worker still raises its recovery notice; allowing a wait never suppresses it. Oracles: `todo_dispatch.wait.test.ts`, `todo_dispatch.test.ts`.

## Critical-chain split before wait

With free worker capacity and no dispatchable rows, `wait` is refused once per plan revision when a critical pending row depends only on running rows (a lone running critical row with nothing parked behind it may wait). While the user is away, the ordered away work list is shown first. The refusal names those rows and asks for `todo` op `append` to split parallel parts while preserving the current worker's partial output, followed by dispatch. Adding rows or dropping dependencies answers the demand; an unsplittable chain can answer with `override: "idle-wait: <reason>"`. The same structure does not repeatedly block. Existing wait gates still require ready split rows to be staffed.

Both the refusal and PLAN CHECK ask to restaff a critical worker only when a live `:free` model or `low`/`minimal` effort conflicts with its effective role policy. Permitted mechanical low/free routes and operator `task.maxEffort` caps never warn. Identity comes from the running session's `session_init.agent` (the public job snapshot has no profile); model and effort come from the live registry session. Core agent discovery supplies project/user/extension precedence, and core model resolution applies `task.agentModelOverrides` and configured role aliases. Unknown identity or unresolved model policy cannot prove a model mismatch. Measured-failure recovery remains independent. Oracle: `todo_dispatch.wait.test.ts` (`critical split:`).

## Complete actionable backlog context

Every `todo_dispatch` developer context MUST include every pending, in-progress and blocked TODO row, including rows beyond the former 64-row display bound, in canonical order with exact owners, dependencies, estimate revisions, reestimate counts and durable attempt history. Only closed rows may be omitted. All nonclosed forecasts and planning issues remain visible. Repeated estimate changes MUST remain failure evidence when a revised ETA is no longer overdue; inspect failed attempts and receipts and choose a concrete recovery action or explain a genuine wait, rather than clear the warning by editing the ETA. The model MUST act on ready unstaffed rows within actual capacity or explain the real dependency/approval wait; healthy running owners and external approvals MUST NOT be re-dispatched or forced into slot-filling replans. Admission remains advisory and must not skip otherwise legal progress. Oracle: `todo_dispatch.gates.test.ts` registered admission context and approval/dependency controls.

After a restart, an `in_progress` row whose owner matches no running task job, no persisted child the current process still knows, and no running external wait is lost/unstaffed. A persisted roster entry unknown to the current process does not count as a running owner. The context lists such a row under `Lost/unstaffed in-progress owners`, the plan snapshot keeps `runs` = `no`, missed-ETA alarms stay armed, and the row stays dispatchable. Oracle: `todo_dispatch.test.ts` ("resumed in-progress owner with zero live jobs is lost and unstaffed").

After any number of compactions the model context MUST retain only the newest copy of each of these three custom types WHEN PRESENT: `chief-rules-after-compaction`, `worker-brief-after-compaction`, and `todo-error-reminder`; older copies never reach the model. The session journal stays append-only: `session_compact` reinjects the chief runbook in main sessions or the original worker brief in worker sessions only when the canonical post-compaction context dropped the respective type. Canonical context-builder errors surface rather than trigger duplicate reinjection. The `context` hook returns the filtered latest-wins view even on single-writer-lane, missed-deadline, and no-prompt early returns. The all-three-seeded, five-compaction oracle still requires exactly one copy of each type: `todo_dispatch.test.ts` (`extension-only context accumulation regression`).

## Event-woken turns and file safety

9. **Repeated event-woken status does not reach the user twice.** Only worker-result, IRC, or harness-notice wakeups are event-woken; user-initiated turns are never collapsed. Normalize digits, hex ids/SHAs, and worker names, lowercase, then collapse a final reply whose token-set overlap with the previous user-visible reply is at least 0.8 to one dim `(no change: status repeated)` line and one chief notice. Also collapse event-woken replies with at most six tokens and no digit, SHA, or URL. A duplicate receipt with the same worker id and result-text hash starts no new turn. A new SHA remains visible. Oracles: `event-controller-message-start.test.ts`, `agent-session-async-delivery.test.ts`.
10. **One non-isolated writer per checkout.** A `coder`, `ui-coder`, `workhorse`, or `git-pr-owner` may run alongside another non-isolated writer only when the canonical latest TODO rows match each exact spawn key as owner and their explicit resources prove disjoint real Git checkout roots. Resource prefixes, role suffixes, file paths and symlink aliases resolve to the checkout root. Freeze that scope at dispatch; later plan changes cannot move an active writer's ownership. Missing or ambiguous proof retains the whole-session refusal. Check every active writer, name a conflicting worker and suggest `isolated: true`. Isolated writers remain allowed. Oracles: `agent_router.test.ts`, `structured-subagent.test.ts`.
11. **File writes cannot silently destroy tracked content.** Refuse empty writes and writes under 5% of an existing tracked file's byte size unless the call explicitly sets `replace: true`; the refusal names the path and reason. Real files only: internal control URIs (`proc://`, `agent://`, `xd://`, any non-file scheme) never get this guard, so `write proc://<id>/kill` with empty or omitted content always passes (R3). Writes and edits anywhere else pass, including other repositories: sessions work on every repository from tasks-loop. Oracle: `agent_router.test.ts`.
12. **A wake requires new information.** A harness notice with the same rendered content for the same row/kind is appended silently and does not start a chief turn; retro-due emits once per trigger key until that key changes. Empty event-woken assistant finals are not rendered. A new worker failure still wakes the chief. Oracles: `todo_dispatch.wait.test.ts` (repeat notices and failure wake), `todo_dispatch.retro.test.ts` (retro trigger lifecycle), `event-controller-message-start.test.ts` (empty TUI final).

## First-slip intervention (R1-R4)

Live 2026-10-03: case A row "Force-layout callouts" (worker IntegrateFacilityCallouts on ui-coder) ran 65m with 4 reestimates while the chief only moved the ETA and its `write proc://IntegrateFacilityCallouts/kill` was refused by the file guard; case B row "Report r8 REQ-7 and REQ-11 fails fixed" (worker FixR8LastFails) hid behind its 5th reestimate.

- **R1.** When a row is `in_progress` with a running owner and is past its ETA (overdue, or the budget from `todoOverrunBudgetMs` is exceeded), a `todo schedule` that changes that row's estimate while keeping the same owner is refused unless the update carries `evidence` (the failure reason) plus the new estimate. The bare refusal is one exact action: schedule the row with evidence plus a new estimate, or with a new owner — the `-strong` variant of the worker's agent when one exists, or split the remainder into new rows. An update that changes the owner in the same call, or that drops or splits the row, is allowed. Oracle: `todo_dispatch.gates.test.ts` ("R1 (case A)").
- **R2.** A row with `reestimateCount` ≥ 3 under the same owner cannot be reestimated again under that owner at all, overdue or not; the former EXHAUSTED-at-5 prompt text is superseded by this refusal. The R1 exceptions (owner change, drop, split in the same call) stay allowed. Oracle: `todo_dispatch.gates.test.ts` ("R2 (case B)").
- **Owner-local reestimates.** The canonical `todo schedule` path resets `reestimateCount` to 0 when the normalized owner changes (including clearing it). An estimate supplied with that owner change starts the new owner's budget at 0; subsequent changed estimates increment it. Resending the same normalized owner does not reset the budget. `estimateRevision` and append-only `attemptHistory` retain the row's full history. Restaffing an exhausted row therefore permits the next schedule under its new owner; three reestimates under the same owner still refuse. Oracles: coding-agent `todo-schedule.test.ts` and `todo_dispatch.gates.test.ts` ("owner recovery").
- **R3.** `write proc://<id>/kill` with empty or omitted content is never blocked by the empty-content and shrink guard in `agent_router.ts`; the same holds for every internal control URI (`proc://`, `agent://`, `xd://`, any non-file scheme). The guard applies only to real files (row 11). Oracle: `agent_router.test.ts` ("R3").
- **R4.** Refusal and PLAN CHECK texts follow the gate-message rule: one exact tool call sequence, no essay (a single "Refusing" sentence naming the exact calls). The calls a refusal names must pass `decideGateCall` while an escalation gate stands: no gate may demand a todo-only turn that another gate refuses. Oracle: `todo_dispatch.gates.test.ts` ("R4").
- **Empty ready lists.** Worker-work refusals suggest a task call only when dispatchable rows exist; parked or waiting rows still receive the `unit:<name>` / `job:<pid>` owner guidance without an empty `for: .` sentence. Oracle: `todo_dispatch.gates.test.ts` ("empty dispatchableReady").

## Notice delivery

Harness, router and deadline notices are passive asides (`triggerTurn: false`): they join the next real turn while idle and the next provider input while streaming. Informational notices also use `interruptWait: false` on hosts supporting that option. Recovery obligations for stuck workers may interrupt a running wait; they never start an idle turn. The overdue-plan alarm is an explicit wake (`triggerTurn: true`). Compaction restores rules and worker briefs through the existing passive `nextTurn` channel.
